# negative-test-first

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Format: agent skill](https://img.shields.io/badge/format-SKILL.md-orange)](SKILL.md)
[![Discipline: negative test first](https://img.shields.io/badge/дисциплина-негатив%20тест%20первым-2ea44f)](SKILL.md)

Скилл для агентов-программистов: общая дисциплина тестирования любого
продукта, у которого есть заявления, которые обязаны выполняться. Бизнес-правила
(«нельзя списать больше, чем на счету»), инварианты данных («баланс равен сумме
движений»), переживаемость состояния («данные не теряются при рестарте»),
параллельная работа («не задвоить списание»), контракты API, разграничение
доступа и аудит — всё, где «фича работает» ничего не доказывает, а доказывает
только «нарушить не получилось».

Скилл вырос из реальной практики: разработки расширения разграничения доступа
для PostgreSQL, где каждый механизм защиты обязан иметь негативный тест, а
каждый сбежавший дефект превращается в именованный урок, который живёт в
комментариях кода и в тестах. Не учебная теория — выстраданный чеклист того,
что ломалось и как это стали ловить.

## Главная мысль

Требование считается покрытым, только когда тест показал: **нарушить не
получится**. Тест, который проверяет только счастливый путь, не доказывает
ничего о правиле. На каждое заявление — «списать больше баланса нельзя»,
«только роль X может писать в таблицу T», «данные переживают рестарт» —
должен существовать тест, который попытался это нарушить: на границе,
за границей, параллельно, через обходной путь — и не смог.

Обычный порядок обратный: сначала позитив («фича работает»), а негативы
«если останется время». Здесь наоборот: негатив пишется первым, позитив —
дешёвая половина. Безопасность — не отдельная тема, а самый острый случай
той же дисциплины: там заявление без негативного теста — это заявление,
которое никто не проверял ни разу.

## Что внутри

Три слоя: универсальная таблица «заявление → обязательный негатив» (семь
видов заявлений: условие работы фичи, бизнес-правило, инвариант данных,
переживаемость состояния, контракт API, параллельность, безопасность),
девять паттернов и восемь антипаттернов. Коротко о паттернах:

* каждое требование парно с негативным тестом — список заявлений становится
  индексом покрытия: у каждого заявления имя нарушающего его теста;
* классы входов перечисляются и проверяются по отдельности, а не «примером
  плохого значения»: пусто, один, много, на границе, за границей — ошибки
  на единицу живут ровно на границе;
* после ожидаемого отказа проверяется, что мир не изменился: ничего не
  создалось, не списалось, не посчиталось — частично применённый отказ это
  баг в одежде теста;
* отказ классифицируется: **кто** отказал — наш код, платформа, драйвер,
  опечатка; «поймали какое-то исключение» не считается;
* ветвление по платформам честное: если на другой сборке раньше срабатывает
  платформа, тест так и пишет («наша проверка — защита в глубину»), а не
  выдаёт зелёный свет ни за что;
* свидетельства отказа проверяются в двух каналах: то, что умирает вместе с
  транзакцией, и то, что её переживает (серверный журнал);
* негативы повторяются после миграции на живых данных — обновление, тихо
  ослабившее правило, хуже бага: это регресс с зелёным релизом;
* пороги производительности выводятся из A/B-базлайна, а абсолютные лимиты
  действуют только при доказанной тишине на машине;
* счёт точный («57 OK, 0 FAIL», провалы поимённо), релиз стоит до зелёного
  прогона на всех стендах, а сбежавший дефект становится именованным уроком.

## Установка

Скилл нейтрален к платформе агента — это `SKILL.md` с описанием принципов
и паттернов.

```bash
# OpenCode и совместимые: каталог скиллов
git clone https://github.com/Bra1nZ/negative-test-first
cp -r negative-test-first ~/.config/opencode/skills/negative-test-first
```

Для агентов, читающих скиллы из других мест, положите `SKILL.md` туда, где
агент ищет скиллы. Скилл активируется сам, когда задача про план тестов для
фичи или продукта, тесты бизнес-правил и инвариантов, проверку покрытия
негативами, классификацию отказов или базлайны производительности.

## Зачем это агентам

Агенты хорошо пишут позитивные тесты и плохо — негативные: они проверяют,
что код делает то, что просят, и почти никогда — что код отказывает тому,
о чём не просили. Чем дороже цена нарушения правила, тем дороже этот перекос:
зелёный тест-сьют выглядит как «правило работает», хотя ни одна попытка
нарушить его даже не предпринималась. Скилл заставляет спрашивать «какой
тест попытался это нарушить?» до того, как фича объявлена готовой.
